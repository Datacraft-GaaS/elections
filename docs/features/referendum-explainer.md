# Referendum explainer (M68)

Module M68 (`referendum-explainer`) owned by `portal-svc`. Publishes authoritative, accessible explainer content for each referendum question: plain-language summaries, fact-check annotations, multi-language versions, text-to-speech (TTS) audio, and Kenya Sign Language (KSL) video. All public content meets WCAG 2.1 Level AAA accessibility requirements.

## 1. What Referendum Explainer does (vs M49 Referendum Mechanics)

- **M49** (Referendum Mechanics) = the operational election system for referendum elections: ballot counting, result declaration, court interface for referendum petitions.
- **M68** = the public-facing information layer: helps citizens understand what they are voting on before they vote. It consumes `ReferendumQuestion` definitions from M49 and produces accessible explainer content.

M68 is publish-only from a citizen's perspective: citizens read, listen, and watch. No voting happens in M68. The content must be factually neutral and approved by the commissioner before publication.

## 2. Data plane

Four aggregates (per `services/portal-svc/crates/referendum-explainer/src/models.rs` and the M68 spec):

| Aggregate | Purpose | Data class (ADR-0016) |
|---|---|---|
| **ReferendumQuestion** | Mirror of the question from M49: `question_id`, `referendum_cycle_id`, `question_number`, `official_text` (from Kenya Gazette), `ballot_position` (YES / NO or YES / NO / ABSTAIN per referendum type). | C |
| **ExplainerContent** | Explainer for one question in one language: `content_id`, `question_id`, `language_code` (en / sw / ki / luo / kamba / ksl), `content_type` (TEXT / AUDIO / VIDEO), `body_md` (for TEXT), `media_url` (MinIO, for AUDIO/VIDEO), `wcag_level` (AA / AAA), `approved_by_officer`, `approved_at`, commissioner HSM signature. | B |
| **FactCheckAnnotation** | Fact-check annotation on a claim within the explainer: `annotation_id`, `content_id`, `claim_excerpt`, `verdict` (TRUE / FALSE / MISLEADING / CONTEXT_NEEDED), `source_url`, `annotated_by_officer`, `annotated_at`. | B |
| **PublishedExplainer** | Live published version: `published_id`, `question_id`, `language_content_ids` (JSONB: language_code -> content_id), `published_at`, `version`, `publish_hash` (SHA-256 of all content_ids + approved_at timestamps). | A |

## 3. Accessibility and multi-language model

**WCAG 2.1 Level AAA** is the target for all public explainer pages. Key requirements met:

- Text contrast ratio >= 7:1 (Success Criterion 1.4.6).
- Audio descriptions for all video content (Success Criterion 1.2.5).
- Sign language for all pre-recorded audio content: KSL video is produced per `ExplainerContent` with `language_code = ksl` (Success Criterion 1.2.6).
- Reading level <= Grade 8 (Flesch-Kincaid Grade Level) for EN and SW text (Success Criterion 3.1.5 - Reading Level).
- TTS audio is generated by a local NLLB-aligned TTS model served by `ml/vault` (192.0.2.11, Ollama) for Swahili, Kikuyu, Luo, and Kamba; EN uses a standard TTS engine.

Languages published: EN, SW (required); KI (Kikuyu), LUO, KAMBA (targeted); KSL video (required for AAA).

## 4. Pipeline

Files on disk under `services/portal-svc/crates/referendum-explainer/src`: `lib.rs`, `models.rs`, `content.rs`, `factcheck.rs`, `publish.rs`, `routes/`.

```
M49 emits eel.governance.referendum_question_defined.v1
      -> M68 creates ReferendumQuestion mirror
      -> content team drafts ExplainerContent per language:
            -> TEXT: body_md authored in CMS (Django)
            -> AUDIO: TTS generated from body_md via TTS service
            -> VIDEO: KSL recording uploaded to MinIO
      -> fact-check team annotates each TEXT content:
            -> FactCheckAnnotation per claim
            -> MISLEADING or FALSE annotation blocks approval
      -> content officer approves each ExplainerContent:
            -> WCAG audit run (automated: aXe-core via Playwright)
            -> Reading Level check (Flesch-Kincaid, < Grade 8 required)
            -> commissioner signs approved content with HSM
      -> when all required languages approved (EN + SW + KSL minimum):
            -> PublishedExplainer assembled
            -> publish_hash computed
            -> public portal updated
            -> emit eel.portal.explainer_published.v1
      -> post-publication: fact-check annotations visible to public as
         inline badges on the explainer page
```

| `POST /v1/referendum-explainer/questions/{id}/publish` | Content officer | Publish approved explainers |
| `GET /v1/referendum-explainer/questions/{id}/publish-hash` | Court registrar, IAB | Verify publish hash for content integrity |

## 7. Integrity + anti-tamper

- **HSM-signed content**: each approved `ExplainerContent` is signed by the commissioner; the signature covers `SHA-256(content_id || body_md || approved_at)`. The public portal displays the signature date; any alteration after approval is detectable.
- **Publish hash**: `PublishedExplainer.publish_hash` covers all content IDs and their approval timestamps; the court registrar can verify the hash to confirm that published content matches what the commissioner approved.
- **MISLEADING/FALSE annotation gate**: a content item with any `FactCheckAnnotation` verdict of `FALSE` or `MISLEADING` cannot be approved; the API returns HTTP 422 with `PENDING_FACT_CHECK_RESOLUTION` until the content is revised.
- **WCAG automated gate**: the aXe-core accessibility scan (Deque Systems, aXe-core open source) must return zero Level AAA violations before content is eligible for approval; this is enforced in the approval pipeline, not just at deployment time.
- **Audit shadow**: all content creation, annotation, approval, and publish events logged to `eel_portal_audit_shadow`.

## 8. Kenya statute alignment

- **Constitution of Kenya 2010 Art 74 (referendum)**: voters have the right to understand what they are voting on; M68 is the Commission's mechanism to fulfil this public interest obligation.
- **Election Campaign Financing Act 2013 (neutrality)**: explainer content must not advocate for a YES or NO outcome; the fact-check annotation system flags advocacy language. Content officer and commissioner approval chain enforces neutrality.
- **Persons with Disabilities Act 2003 §21 (accessible information)**: KSL video and WCAG 2.1 AAA compliance satisfy the statutory obligation for accessible electoral information.
- **Official Languages Act 2016 (Swahili)**: SW is a co-official language; SW explainer content is required, not optional.

## 9. Honest caveats + external prerequisites

- KSL video production requires contracted KSL interpreters; M68 manages the upload and approval workflow but does not produce the KSL video itself. the Commission must contract qualified KSL interpreters before any referendum cycle.
- TTS audio quality for Kikuyu, Luo, and Kamba depends on the NLLB-based TTS models available on the ml/vault server. These are lower quality than commercial TTS for these languages; the Commission should assess whether the audio quality is sufficient for the target literacy level before relying on TTS alone.
- Flesch-Kincaid Grade Level is calibrated for English; the SW, KI, LUO, and KAMBA text reading level checks use an approximate adaptation and should be reviewed by a literacy specialist before publication.
- The content approval workflow assumes the commissioner has the capacity to sign each approved content item individually; for a complex referendum with many questions and six language variants, this could be several dozen HSM signing operations.
- Fact-check officers must be independent of the content creation team; M68 enforces SpiceDB role separation but does not enforce organisational independence.

### Content approval gate matrix

| Check | Tool | Pass condition | Enforcer |
|---|---|---|---|
| WCAG 2.1 AAA (automated) | aXe-core (Deque Systems, v4.x) | Zero Level AAA violations | Approval pipeline |
| Flesch-Kincaid Grade Level | `flesch_kincaid` crate | Grade <= 8 (EN/SW) | Approval pipeline |
| Fact-check annotation gate | Manual review | No `FALSE` or `MISLEADING` annotations unresolved | Application layer |
| Neutrality review | Manual review by legal officer | No advocacy language detected | Application layer |
| Commissioner HSM signature | HSM | Valid signature over content hash | Approval API |

All five checks must pass before `ExplainerContent.status` can transition to `APPROVED`. The pipeline fails fast: the first failed check blocks the approval step and returns a descriptive error to the content officer.

### Multi-language publication readiness

The `POST /v1/referendum-explainer/questions/{id}/publish` endpoint accepts publication only when:

- EN + SW + KSL content items are `APPROVED` (minimum required set).
- Each of the above content items has at least one `FactCheckAnnotation` with verdict `TRUE` per major factual claim.
- No content item has an unresolved annotation with verdict `FALSE` or `MISLEADING`.

KI, LUO, and KAMBA explainers are optional; if not present at publication time, the public portal shows a "not yet available in this language" banner for those languages with an ETA date configured by the content officer.
