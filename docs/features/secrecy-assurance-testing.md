# Secrecy assurance testing (M61)

Module M61 (`secrecy-assurance-testing`) owned by `ai-platform-svc`. Manages adversarial red-team engagements on isolated staging clones to test ballot secrecy, coercion resistance, and vote-buying attack surfaces. Each engagement runs against a dedicated staging clone with no connection to production. Independent Audit Board (IAB) attestation is required before any finding can be closed.

## 1. What Secrecy Assurance Testing does (vs M26 Anomaly/Fraud Detection)

- **M26** (Anomaly and Fraud Detection) = continuous monitoring of production data streams for anomalies during the election. It is passive and reactive.
- **M61** = proactive adversarial testing on isolated clones, conducted before the election. It is active and offensive.

M61 findings that reveal production design flaws are escalated to the relevant engineering team and tracked as blocking issues; M26 monitors whether those flaws reappear in production after remediation.

Three aggregates (per `services/ai-platform-svc/crates/secrecy-testing/src/models.rs` and the M61 spec):

| Aggregate | Purpose | Data class (ADR-0016) |
|---|---|---|
| **RedTeamEngagement** | Top-level engagement: `engagement_id`, `engagement_type` (BALLOT_SECRECY / COERCION_RESISTANCE / VOTE_BUYING / INSIDER_THREAT / SOCIAL_ENGINEERING), `lead_tester`, `staging_clone_id`, `scope_md` (which modules and attack surfaces are in scope), `started_at`, `completed_at`, `status` (PLANNED / ACTIVE / REMEDIATION / ATTESTED / CLOSED). | A |

## 3. Staging clone isolation

Each `RedTeamEngagement` references a `staging_clone_id`. Clone isolation requirements:

- The staging clone is a separate Kubernetes namespace (`eel-staging-clone-{engagement_id}`) with its own Postgres instance, Kafka cluster, and S3 bucket. No network path to production namespaces exists.
- Clone data is synthetic: generated by the `tools/synthetic-data-generator` with configurable voter counts and election results. No production voter biometrics or real personal data are used.
- Clone credentials (DB passwords, API keys, JWT secrets) are issued per-engagement from a dedicated Vault path and rotated when the engagement closes.
- Clone destruction: when an engagement reaches `ATTESTED` or `CLOSED`, the Kubernetes namespace is torn down and all clone data is deleted. A destruction receipt is stored in `RedTeamEngagement.clone_destroyed_at`.
- Network isolation is enforced via Kubernetes `NetworkPolicy` objects that deny all ingress from non-clone namespaces and all egress to production IP ranges.

## 4. Pipeline

Files on disk under `services/ai-platform-svc/crates/secrecy-testing/src`: `lib.rs`, `models.rs`, `engagement.rs`, `finding.rs`, `attestation.rs`, `routes/`.

```
security team schedules RedTeamEngagement (type + scope + lead_tester)
      -> IAB liaison approves engagement scope
      -> staging clone provisioned (Kubernetes namespace + synthetic data)
      -> emit eel.ai.red_team_engagement_started.v1
      -> red team executes attacks against clone endpoints
      -> Finding records created for each vulnerability discovered
            -> CRITICAL finding: emit eel.ai.critical_finding.v1
               -> engineering lead + IAB notified immediately
      -> remediation phase: engineering team addresses findings
      -> IAB member reviews each remediated or risk-accepted finding
            -> creates IABAttestation with HSM signature
      -> engagement moves to ATTESTED when all findings have attestation
      -> emit eel.ai.engagement_attested.v1
      -> staging clone destroyed; clone_destroyed_at recorded
      -> emit eel.ai.engagement_closed.v1
```

## 7. Integrity + anti-tamper

- **IAB attestation gate**: a Postgres `CHECK` constraint on `findings` enforces that `status IN ('FIXED', 'RISK_ACCEPTED')` requires a non-null `iab_attestation_id`. No application code can close a finding without an attestation.
- **HSM-signed attestations**: the IAB member HSM signature covers `SHA-256(attestation_id || finding_id || attestation_type || evidence_md)`; any post-signature alteration is detectable.
- **CVSS scoring**: all findings carry a CVSS v3.1 vector string (FIRST.org CVSS v3.1 Specification Document, 2019); the scoring is validated by the `cvss31` crate against the FIRST specification.
- **Clone network isolation**: CI enforces that the staging clone namespace has `NetworkPolicy` deny-all before each engagement; a missing policy fails the engagement activation step.
- **Clone destruction audit**: `RedTeamEngagement.clone_destroyed_at` must be set before `status = CLOSED`; the application blocks closure without destruction confirmation.
- **Audit shadow**: all aggregate mutations logged to `eel_ai_audit_shadow`.

## 8. Kenya statute alignment

- **Elections (Technology) Regulations 2017 Regulation 6 (system testing)**: pre-election security testing is required; M61 produces the engagement records and IAB attestations that satisfy Regulation 6.
- **Constitution of Kenya 2010 Art 86(a) (ballot secrecy)**: ballot secrecy is a constitutional requirement; M61 specifically tests for secrecy vulnerabilities (coercion resistance, vote-buying attack surfaces).
- **Kenya Data Protection Act §29 (data security)**: the no-real-data-in-staging rule (synthetic data only) ensures ODPC obligations on real voter data are not implicated by red team activities.

## 9. Honest caveats + external prerequisites

- Red team testers must be formally contracted security professionals with non-disclosure agreements; M61 manages the engagement records but does not manage the procurement of red team services.
- IAB members must have HSM tokens provisioned by the same key management infrastructure as commissioners. Provisioning IAB HSM tokens is an operational task.
- Staging clone provisioning requires Kubernetes cluster capacity above the production baseline. IEBC infrastructure must have reserved capacity for clone namespaces during the pre-election testing window.
- M61 tests ballot secrecy in the software layer. Physical ballot secrecy (e.g., polling booth design, scrutineering rules) is outside scope.
- A CRITICAL finding blocks the election system from proceeding to the next readiness gate until IAB attests it is fixed or risk-accepted. This creates a hard dependency between M61 and the election readiness timeline.

### Engagement type to attack surface mapping

| Engagement type | Attack surfaces in scope | Key threat model |
|---|---|---|
| BALLOT_SECRECY | BVI kit, ABIS result, polling booth data flow | Vote traceability; linking voter identity to ballot |
| COERCION_RESISTANCE | `*400#` USSD, BVI fallback PIN mode | Coercer observing or recording voter's choice |
| VOTE_BUYING | M47 nomination fee flow, M22 finance disclosure | Cash-for-vote coordination channels |
| INSIDER_THREAT | Admin panels, commissioner HSM access, staff M55 records | Privileged user manipulating results or voter records |
| SOCIAL_ENGINEERING | Staff training (M38), email/phone phishing simulations | Credential compromise via non-technical attack |

### Pre-election readiness gate

M61 findings gate the overall election readiness assessment. The readiness checklist item `SEC_ASSURANCE_ATTESTED` is checked by the IAB liaison only when:

- All `RedTeamEngagement` records for the current election cycle have `status = ATTESTED`.
- No `Finding` with `severity = CRITICAL` has `status = OPEN`.
- No `Finding` with `severity = HIGH` has `status = OPEN` for more than 30 days.

The readiness dashboard (M15 IAB Dashboard) surfaces this gate status in real time.

### Key metrics and SLOs

| Metric | Target | Alert threshold |
|---|---|---|
| Engagement-to-attestation cycle time | <= 45 days | > 60 days: escalate to IAB chair |
| CRITICAL finding mean time to remediation | <= 14 days | > 21 days: readiness gate blocked |
| Clone destruction time after engagement close | <= 24 h | > 48 h: alert to security lead |
| IAB attestation per finding turnaround | <= 7 days | > 10 days: escalate |
