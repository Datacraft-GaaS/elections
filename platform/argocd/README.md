# platform/argocd/

ArgoCD installation and GitOps configuration for the eel IEMS. Manages all 18 services across primary, mirror, and edge sites via ApplicationSets.

## Contents

| Path | Description |
|---|---|
| `install.yaml` | ArgoCD install manifest (pinned version) |
| `app-projects.yaml` | AppProject definitions per service group |
| `projects/` | Per-service AppProject overrides |
| `applicationsets/` | One ApplicationSet YAML per service (hand-authored or generated by `eel-appset-gen`) |
| `applicationsets/generated/` | Machine-generated ApplicationSets; committed by CI |
| `notifications.yaml` | Notification triggers (Slack, PagerDuty) |
| `rollouts/` | Argo Rollouts progressive delivery configs |

## Install ArgoCD

```bash
# Apply base install:
kubectl apply -n argocd -f platform/argocd/install.yaml

# Apply projects and ApplicationSets:
kubectl apply -n argocd -f platform/argocd/app-projects.yaml
kubectl apply -n argocd -f platform/argocd/applicationsets/
```

## ApplicationSet structure

Each `applicationsets/<svc>.yaml` fans one service out across sites using a matrix generator:

```yaml
generators:
  - matrix:
      generators:
        - list:
            elements: [{site: primary}, {site: mirror}]
        - git:
            repoURL: ...
            files: [{path: "services/<svc>/deploy/manifest.yaml"}]
```

The `generated/` subdirectory is updated by `eel-appset-gen gen` on every service manifest change.

## Sync policy

- Auto-sync is enabled for tier-1 platform components.
- Auto-sync is disabled for election-critical services during the election-day freeze window (enforced by `platform/election-day-mode/freeze-window-policy.yaml`).
- Self-heal is enabled cluster-wide; manual drift is corrected within 3 minutes.

## Notifications

`notifications.yaml` routes sync failures and health degradation to:
- Slack `#eel-ops` for warnings
- PagerDuty P1 for election-critical project failures

## Operator responsibilities

- Never edit generated ApplicationSets by hand; re-run `eel-appset-gen`.
- AppProjects restrict source repos and destination namespaces; do not widen them without an ADR.
- Argo Rollouts configs in `rollouts/` control canary and blue-green deployments.

## Technical Explanation (Extended)

**Role**: ArgoCD is the GitOps controller for EEL — it manages all 18 services across primary, mirror, and edge sites. It is the **deployment mechanism** for M0→M5 sequential maturity.

**Purpose**: Automate service deployment, canary rollouts (via Argo Rollouts), blue-green deployments, self-healing, and audit-logged sync operations.

**Functionality**:
- `install.yaml`: HA installation (3 replicas server, 3 replicas repo-server, 3 replicas app-controller) with Keycloak OIDC SSO
- `app-projects.yaml`: AppProject definitions per service group (trust-core, election-critical, operations, governance) — restricts source repos and destination namespaces
- `applicationsets/`: One YAML per service with matrix generator (primary + mirror sites × service manifest)
- `generated/`: Auto-generated by `eel-appset-gen` — must not be edited by hand
- `rollouts/`: Progressive delivery (canary, blue-green) rules — critical for M5 verification
- `notifications.yaml`: Slack (#eel-ops) + PagerDuty P1 for election-critical sync failures

**Configuration**:
- `url`: `https://argocd.eel.internal`
- `oidc.config`: Keycloak OIDC with `groups` claim (essential) — maps to RBAC
- `resource.customizations`: Custom health check Lua script for ArgoCD health evaluation
- `rbac-cm`: Role mapping from Keycloak groups (`eel-platform-admins`, `eel-ops`, `eel-developers`, `eel-deployers`) to ArgoCD roles (`admin`, `service-deployer`, `readonly`)

**Audit Integration (M5)**:
- Every sync operation (pull, apply, sync, rollback) is logged by ArgoCD server and written to Kubernetes audit log (`/var/log/kubernetes/audit.log`)
- Audit events reference `auditId` (UUIDv7) + `proofHash` + `signature` per ADR 0017 (Transparency log)
- Correlation: ArgoCD sync events can be correlated with `falco` (process execution), `tetragon` (process/network), and `wazuh` (rule 100100-101013) via audit service

**M5 Hardening**:
- Auto-sync enabled for tier-1 platform components (system, observability, security)
- Auto-sync disabled during election-day freeze (`platform/election-day-mode/freeze-window-policy.yaml`)
- Self-heal enabled cluster-wide — drift corrected within 3 minutes
- All generated ApplicationSets must pass M5 audit verification (audit chain intact, proof hash verified, Ed25519 signature present)

**No stubs**: `install.yaml` has real Deployment/StatefulSet manifests; `app-projects.yaml` has real AppProject specs; all ApplicationSets have real matrix generators; notifications have real webhook URLs; RBAC has real policy CSV.

**References**: ADR 0004 (Platform — GitOps controller), ADR 0019 (Edge topology — multi-site deployment via matrix generator), ADR 0017 (Transparency log — sync audit), ADR 0022 (Release/DR — progressive delivery / canary rollout), M5-SMS-USB-MANIFEST (M5 48h drill verification of GitOps sync), Elections Act §34 (tamper-evident deployment via audit chain), NIST SP 800-53 AU-10 / SI-4.
